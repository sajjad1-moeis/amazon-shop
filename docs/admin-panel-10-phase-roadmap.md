# نقشه راه پیاده‌سازی پنل ادمین — ۱۰ فاز

این سند فازبندی اجرای **تمام موارد درخواستی کارفرما** برای پنل ادمین را مشخص می‌کند. هر فاز باید با **سورس فعلی** (`Next.js` ادمین، سرویس‌ها، الگوی `AdminLayout`، `adminSidebarData`، کامپوننت‌های مشترک مثل `AdminPageHeader`، `AdminSectionCard`) هم‌راستا باشد.

---

## اصول غیرقابل‌تخطی (همهٔ فازها)

1. **ظاهر کلی پنل**  
   تغییرات **تدریجی و کم‌ریسک**: همان پس‌زمینه، سایدبار، تایپوگرافی و فاصله‌گذاری فعلی حفظ شود. فقط **افزودن آیتم منو**، **صفحه/بخش جدید** یا **تکمیل همان صفحات موجود**؛ بدون بازطراحی کلی یا جابه‌جایی شدید چیدمان بخش‌های سالم.

2. **عدم شکستن رفتار فعلی**  
   مسیرها و فیچرهایی که الان کار می‌کنند باید پس از هر فاز **همان‌طور که بود** در دسترس بمانند (سازگاری عقب‌رو با URLها و APIهای موجود).

3. **محدوده تغییر**  
   **فقط پنل ادمین** (مسیرهای `app/admin/**`، قالب‌های `template/Admin/**`، سرویس‌های مخصوص ادمین، و **APIهایی که صرفاً برای ادمین** لازم است).  
   *استثناء فنی:* برای دادهٔ لازم، **اندپوینت‌های بک‌اند جدید یا توسعهٔ اندپوینت‌های موجود** در همان بک‌اند پروژه مجاز است؛ اما **UI سایت عمومی، فروشگاه کاربر، چک‌اوت و … تغییر نکند** مگر صراحتاً برای تأمین دادهٔ ادمین ضروری باشد (در آن صورت حداقل تغییر و بدون تغییر قرارداد عمومی).

4. **یکپارچگی بصری**  
   آیتم‌های جدید از **همان الگوهای موجود** استفاده کنند: کارت‌های تیره، بوردر `gray-600/700`، دکمه‌ها و فرم‌های هم‌سبک ادمین، `Spinner`، `toast`، جدول‌های هم‌خانواده با `OrdersTable` / `UsersTable` و فیلترهای `FilterSection` در حالت `isAdmin`.

5. **کیفیت پیاده‌سازی**  
   - اتصال **کامل فرانت به بک‌اند** (بدون mock دائمی در production).  
   - **عملکرد:** صفحه‌بندی، جلوگیری از query سنگین بدون فیلتر بازه، کش منطقی در سمت سرور جایی که API اجازه می‌دهد، lazy load برای تب‌های سنگین.  
   - **امنیت:** همهٔ اندپوینت‌های حساس فقط با **نقش ادمین**؛ اعتبارسنجی ورودی؛ عدم افشای کلید/رمز در پاسخ یا لاگ کلاینت.  
   - **منطق مالی/حسابداری:** هر جمع، فیلتر «سفارش موفق»، واحد پول (تومان) و بازهٔ زمانی در بک‌اند **یک‌بار و شفاف** تعریف شود؛ فرمول نرخ تبدیل ثابت و مستند در API.  
   - **ریسپانسیو:** موبایل/تبلت/دسکتاپ؛ جدول‌ها scroll افقی یا کارت‌محور در عرض کم.

6. **تحویل هر فاز**  
   تست دستی مسیرهای قدیمی ادمین + تست مسیرهای جدید + بررسی لینت/بیلد ماژول ادمین.

## فاز ۱ — آماده‌سازی، قرارداد API و بدون تغییر بصری محسوس ✅ انجام شد

**هدف:** زمینهٔ امن برای فازهای بعد بدون تغییر چشم‌گیر UI.

- مستندسازی الگوی فعلی: `getAuthenticatedClient`، `unwrapApiData`، ساختار پاسخ `{ success, data, message }`.
- تعریف **پیشوند و نام‌گذاری** اندپوینت‌های جدید ادمین (مثلاً `api/admin/...`) هم‌سو با بک‌اند فعلی.
- در صورت نیاز: **کلیدهای دسترسی منو** برای آیتم‌های جدید در سیستم permission موجود (بدون حذف کلیدهای فعلی).
- چک‌لیست رگرسیون: لیست URLهای بحرانی ادمین برای اجرا بعد از هر فاز.

**خروجی:** سند داخلی کوتاه + آماده‌سازی شاخهٔ API؛ **صفحهٔ کاربری ادمین از نظر ظاهر مثل قبل**.

**تحویل فاز ۱:**

| مورد | مسیر |
|------|------|
| راهنمای توسعه‌دهنده (API، کلاینت، ساختار ادمین) | `docs/admin-developer-handbook.md` |
| چک‌لیست رگرسیون URL | `docs/admin-regression-checklist.md` |
| رزرو `key` منو برای فازهای ۲–۱۰ | `src/constants/adminPlannedMenuKeys.js` |
| ارجاع در کد | توضیح بالای `adminSidebarData.js`، JSDoc روی `getAuthenticatedClient` / `unwrapApiData` در `client.js` |

## فاز ۲ — سفارشات: گروه عملیاتی و زیرمنو (سازگار با لیست فعلی) ✅ انجام شد

**هدف:** منوی «سفارشات» با زیرمنوهای پیشنهادی کارفرما؛ همان `OrdersTable` و فیلترها.

- به‌روزرسانی `adminSidebarData.js`: زیرمنوها با `href` به `/admin/orders?status=...` (یا معادل enum بک‌اند) مطابق وضعیت‌های موجود.
- اطمینان از اینکه **صفحهٔ واحد سفارشات** با query پارامتر همان داده را نشان می‌دهد (در صورت اختلاف نام وضعیت، نگاشت در فرانت یا یکسان‌سازی با API).
- بدون حذف مسیر `/admin/orders` بدون پارامتر (همه سفارشات).

**بک‌اند:** در صورت نیاز فقط **پشتیبانی از فیلتر وضعیت** که احتمالاً هست؛ در غیر این صورت تکمیل پارامترها.

**ریسپانسیو:** منوی تاشو موبایل همان رفتار فعلی سایدبار.

**تحویل فاز ۲:**

| مورد | مسیر / توضیح |
|------|----------------|
| زیرمنوهای سفارش | `src/data/adminSidebarData.js` — `?status=1..6` مطابق `OrderStatus` در `orderService.js` |
| highlight سایدبار با query | `src/template/Admin/AdminSidebar.js` — `useSearchParams` + `hrefMatchesLocation` + `Suspense` |
| دراور موبایل | `AdminTopBar.js` — `SideBarContentWithSuspense` |
| سخت‌گیری `status` نامعتبر | `getPaginated` در `orderService.js` — `Number.isFinite`؛ در غیر این صورت لیست همه |
| ریدایرکت مسیرهای قدیمی | `app/admin/orders/{pending,processing,shipped,delivered,cancelled}/page.js` — RSC با `redirect` به `?status=` عددی |

## فاز ۳ — داشبورد (بخش اول): فیلتر بازهٔ زمانی، زمان آخرین بروزرسانی، Refresh، KPIهای اصلی ✅ انجام شد

**هدف:** هم‌راستا با سند داشبورد؛ حفظ استایل کلی صفحهٔ فعلی `admin/page.js`.

- **فیلتر بازه:** امروز، ۷ روز، ۳۰ روز، این ماه، بازهٔ سفارشی؛ نگهداری در URL یا state (ترجیح با URL برای share/bookmark).
- **نوار «آخرین بروزرسانی» + دکمه Refresh** (فراخوانی مجدد همان سرویس‌ها یا اندپوینت تجمیعی).
- **کارت‌های KPI** (در همان grid فعلی یا اضافه‌شونده هم‌سبک):  
  فروش کل (تومان)، سفارشات جدید، سفارشات در انتظار، کاربران جدید، نرخ تبدیل — **همه وابسته به بازه**.
- **بک‌اند:** اندپوینت(های) تجمیعی ادمین با `startDate`/`endDate`؛ تعریف دقیق «سفارش موفق»، «pending»، فرمول نرخ تبدیل **ثابت در سرور**.

**ظاهر:** همان کارت‌های `StatCard` یا نسخهٔ هم‌خانواده؛ رنگ‌های موجود.

**ریسپانسیو:** grid واکنش‌گرا مثل الان.

**تحویل فاز ۳:**

| مورد | مسیر |
|------|------|
| منطق بازهٔ زمانی (محلی، ISO) | `src/lib/adminDashboardDateRange.js` |
| KPI + اولویت `admin/analytics/dashboard-kpi` سپس fallback گزارش‌ها | `src/services/admin/adminDashboardKpiService.js` |
| APIهای اختیاری بازه‌دار | `adminAnalyticsService`: `getSummaryByDateRange`, `getConversionRateByDateRange` |
| UI داشبورد + `?range=` و `from`/`to` | `src/template/Admin/dashboard/AdminDashboardPage.jsx` |
| `Suspense` برای `useSearchParams` | `src/app/admin/page.js` |

**بک‌اند پیشنهادی:** `GET admin/analytics/dashboard-kpi?startDate=&endDate=` — در نبود، فرانت از `Report/GetSalesReport`، `Report/GetUsersReport` و شمارش وضعیت سفارش استفاده می‌کند.

## فاز ۴ — داشبورد (بخش دوم): نمودارها، هشدارهای فوری، empty/loading/error ✅ انجام شد

**هدف:** تکمیل لایهٔ «تحلیل سریع» بدون تغییر هویت بصری.

- **نمودار روند فروش** (خطی/ستونی) با granularity بر اساس طول بازه.
- **نمودار توزیع وضعیت سفارش** (دایره‌ای یا ستونی انباشته) در همان بازه.
- **پنل هشدارها:** سفارش معطل، تیکت بدون پاسخ، خطای ارز/sync، پروکسی، job ناموفق — با رنگ‌بندی و لینک به صفحهٔ مربوط **در همان ادمین**.
- **Loading / skeleton / error** برای هر ویجت؛ **empty state** متنی مثل سند.

**بک‌اند:** سرویس‌های read-only با اولویت‌بندی هشدار؛ بدون منطق مالی روی کلاینت.

**کتابخانه نمودار:** ترجیحاً سبک و هماهنگ با تم تیره (مثلاً همان اکوسیستم پروژه اگر از قبل هست؛ در غیر این صورت اضافه با حداقل bundle).

**تحویل فاز ۴:**

| مورد | مسیر |
|------|------|
| دادهٔ نمودارها و هشدارها (اولویت API ادمین، سپس گزارش/شمارش) | `src/services/admin/adminDashboardChartsService.js` |
| UI نمودارها (Recharts)، اسکلت، خطا، empty، هشدارها | `src/template/Admin/dashboard/AdminDashboardPhase4.jsx` |
| اتصال + `useEffect` جدا با همان `reloadNonce` و بازه URL | `src/template/Admin/dashboard/AdminDashboardPage.jsx` |

**اندپوینت‌های اختیاری بک‌اند (در صورت وجود):** `GET admin/analytics/sales-trend`، `GET admin/analytics/order-status-distribution` — در نبود، از `Report/GetSalesReport` (با تلاش `groupBy` و سپس بازه‌های جزئی) و `OrderCountByStatus` لحظه‌ای استفاده می‌شود. هشدار پروکسی از `GET /api/admin/scraper-proxy/status`؛ تیکت باز از `AdminTicket/GetPaginated`؛ سفارش معطل از KPI همان صفحه ادغام می‌شود.

## فاز ۵ — داشبورد (بخش سوم): سلامت سیستم، خلاصهٔ پروکسی/اسکرپ، جداول اخیر، اکشن‌های سریع 🔄 تحویل اولیه

**هدف:** یک‌دست کردن داشبورد با سند؛ کلیک‌پذیری.

- ویجت **سلامت سرویس‌ها** (sync، ترجمه، ارز، صف job، اتصال منبع) با وضعیت سالم/هشدار/خطا.
- ویجت **خلاصهٔ پروکسی** (لینک به `/admin/scraper-proxy`).
- جدول **آخرین سفارشات مهم** و **آخرین تیکت‌های مهم** (ستون‌ها مطابق سند؛ صفحه‌بندی یا limit).
- **اکشن‌های سریع:** میانبر به صفحات موجود (محصول، sync دستی، ارز، تخفیف، …) فقط اگر endpoint/صفحه آماده است؛ در غیر این صورت در همان فاز یا فاز بعد تکمیل شود.

**قانون:** هر کارت/ردیف قابل کلیک به **مسیر ادمین** مرتبط.

**ریسپانسیو:** جدول‌ها scroll یا stack در موبایل.

**تحویل فاز ۵ (نسخهٔ اول):**

| مورد | مسیر |
|------|------|
| داده: سلامت (اولویت `GET admin/analytics/system-health`، وگرنه ترکیب پروکسی + API + نرخ ارز + ردیف‌های نامشخص sync/ترجمه) | `src/services/admin/adminDashboardPhase5Service.js` |
| UI: کارت سلامت، خلاصه پروکسی، جداول سفارش/تیکت، اکشن‌های سریع | `src/template/Admin/dashboard/AdminDashboardPhase5.jsx` |
| اتصال + `dynamic` + `useEffect` با `reloadNonce` | `src/template/Admin/dashboard/AdminDashboardPage.jsx` |
| یکسان‌سازی درخواست وضعیت پروکسی (فاز ۴ + ۵) | `src/lib/adminScraperProxyStatusFetch.js` |

**سفارشات اخیر:** `Order/GetRecentOrders?count=8`. **تیکت‌ها:** `AdminTicket/GetPaginated` سپس مرتب‌سازی محلی بر اساس `updatedAt`/`createdAt`. **تکمیل بعدی:** ویجت سلامت دقیق sync/job پس از اندپوینت بک‌اند؛ هم‌ترازی بیشتر با سند کارفرما.

## فاز ۶ — ماژول «مدیریت جستجو» (فرانت + بک‌اند کامل)

**هدف:** منوی مستقل + CRUD و گزارش طبق سند کارفرما.

- منوی جدید در `adminSidebarData.js` (آیکن و رنگ هم‌خانواده).
- صفحات/زیرصفحه‌ها: پرجستجو، بدون نتیجه، کم‌کلیک، بدون خرید، **synonym**، **redirect**، اتصال query به دسته/لندینگ، blacklist/whitelist.
- **بک‌اند:** جداول/سرویس ذخیرهٔ قوانین جستجو، APIهای لیست/ایجاد/ویرایش/حذف با اعتبارسنجی و لاگ خطا.

**ظاهر:** فرم‌ها و جدول‌ها مثل بقیهٔ ادمین؛ بدون تم جدید.

**امنیت:** فقط ادمین؛ جلوگیری از XSS در فیلدهای متنی نمایش‌داده‌شده در ادمین.

**پیاده‌سازی (انجام‌شده):**

| بخش | محل |
|-----|-----|
| بک‌اند: موجودیت‌ها، `ApplicationDbContext`، migration `Phase6SearchManagement` | `AmazonShop_Api_Manually` |
| API ادمین: گزارش کم‌کلیک/بدون خرید + CRUD | `GET/POST/PUT/DELETE api/admin/search-management/...` |
| اعمال قوانین روی `SearchProductsAsync` + `SearchResultDto` | `SearchService` |
| پیش‌نمایش قوانین قبل از اسکرپر | `GET api/search/preview-rules` |
| فرانت: منو، هاب، صفحات CRUD و گزارش | `src/app/admin/search/**`، `adminSearchManagementService.js` |
| فرانت: اعمال preview در `/products` | `ProductsClient` + `productService.previewSearchRules` |

گزارش‌های **پرجستجو** و **بدون نتیجه** همچنان از `admin/analytics` (داشبورد)؛ فاز ۶ گزارش‌های کم‌کلیک و بدون خرید را در `/admin/search/reports` اضافه می‌کند.

## فاز ۷ — مدیریت سورس‌ها و اسکرپ + تکمیل/هم‌تراز پروکسی ادمین

**هدف:** شفافیت sourceها مطابق سند؛ هماهنگی با صفحهٔ فعلی پروکسی.

- ماژول **لیست سورس‌ها**: وضعیت، فعال/غیرفعال، quota، خطا، آخرین sync، تست اتصال.
- **بک‌اند:** مدل سورس و APIهای مدیریت؛ اتصال به job/sync در صورت وجود.
- بازبینی `scraper-proxy` فعلی: هر مورد از سند که کم است (success rate، disable دستی، …) **بدون شکستن** تنظیمات فعلی.

**فقط ادمین.**

**پیاده‌سازی (شروع — فاز ۷):**

| بخش | محل |
|-----|-----|
| بک‌اند: موجودیت `ScraperDataSource`، migration `Phase7ScraperDataSources` | `AmazonShop_Api_Manually` |
| API ادمین: لیست/جزئیات/ایجاد/ویرایش/حذف + `POST …/test-connection` | `api/admin/scraper-sources` |
| فرانت: CRUD + تست اتصال | `/admin/sources`، `adminScraperSourcesService.js` |
| منوی اسکرپ: سورس‌ها + پروکسی؛ لینک متقابل در هدر پروکسی | `adminSidebarData.js`، `ScraperProxyAdminPage` |

**تکمیل بعدی فاز ۷:** هم‌ترازی بیشتر با سند کارفرما (موتور غیرفعال دستی در تنظیمات پایتون در صورت API)، اتصال `LastSyncAt` به job واقعی، و در صورت نیاز mirror آمار پروکسی در رکورد سورس.

## فاز ۸ — مرکز Job / Queue / Sync

**هدف:** نمایش و کنترل‌های مجاز ادمین روی jobها.

- UI: صف، موفق، ناموفق، retry/cancel (در صورت پشتیبانی بک‌اند)، sync دستی، آخرین sync موفق، لیست محصولات نیازمند re-sync.
- **بک‌اند:** اندپوینت‌های ایمن؛ idempotency برای اجرای دستی؛ محدودیت نرخ برای جلوگیری از فشار به سیستم.

**لاگ عملیات** در سطح سرور برای پیگیری.

## فاز ۹ — مرکز ترجمه محصول + کنترل کیفیت محصول (QA)

**هدف:** یکپارچه با کاتالوگ؛ بدون دست زدن به UI فروشگاه.

- ترجمه: بدون ترجمه/ناقص، ویرایش، دسته‌ای، fallback، اصطلاحات برند، لاگ خطا.
- QA: بدون تصویر، بدون مشخصات، قیمت غیرعادی، بدون دسته، mapping خطا، تکراری، نیازمند تأیید دستی — **فیلترها و لیست اقدام** در ادمین.
- **بک‌اند:** queryهای بهینه (ایندکس)، به‌روزرسانی محصول از ادمین با validation.

**عملکرد:** صفحه‌بندی، فیلتر، عدم بارگذاری یکجای کل کاتالوگ.

**پیاده‌سازی (فاز ۹):**

| بخش | محل |
|-----|-----|
| بک‌اند: سرویس `AdminProductCatalogTranslationService`، DTOها (`AdminProductCatalogTranslationDtos`)، ایندکس `IX_Products_Phase9_DeletedAt`، migration `Phase9ProductCatalogIndex` | `AmazonShop_Api_Manually` |
| API ادمین: `GET/PUT…` زیر `api/admin/products/catalog` (translation-queue، qa-queue، PATCH title-fa، POST translation/bulk) | `AdminProductCatalogController` |
| فرانت: مرکز ترجمه + QA | `/admin/catalog/translation`، `/admin/catalog/qa`، `adminProductCatalogService.js` |
| منو | زیر «محصولات» در `adminSidebarData.js` |

## فاز ۱۰ — یکپارچه‌سازی، SEO/لندینگ، بلاک‌های صفحه، Audit، گسترش لاگ، مرکز قیمت‌گذاری ✅ پیاده‌سازی اولیه

**هدف:** بستن موارد باقی‌مانده سند؛ همچنان فقط لایهٔ ادمین برای مدیریت (داده ممکن است در بک‌اند مشترک باشد ولی **تغییر UI عمومی نباشد**).

- **API / Integration Center:** API key (masked)، webhook، credential منابع، test connection، وضعیت، callback logs — همه از ادمین.
- **SEO / Landing:** مدیریت لندینگ query، meta، slug، canonical، index/noindex، دسته/برند سئو — طبق مدل دادهٔ بک‌اند.
- **بنر، اسلایدر، بلاک صفحه اصلی:** CRUD، ترتیب، زمان‌بندی؛ استایل فرم‌ها مثل ادمین.
- **Audit trail:** چه کسی چه چیزی را کی تغییر داد (قبل/بعد برای فیلدهای حساس).
- **گسترش لاگ‌ها:** دسته‌بندی (scraper, API, payment, search, …) در همان فضای ادمین؛ بدون حذف «لاگ سیستم» فعلی.
- **مرکز قیمت‌گذاری:** اگر متمایز از `تنظیمات قیمت‌گذاری` است — صفحهٔ هاب با لینک به تنظیمات موجود + هر گزارش/قانون جدید لازم.

**امنیت حداکثری** برای secretها و لاگ‌های حساس.
